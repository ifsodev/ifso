# Threat model

## Assets
- USDG held by `IfsoEscrow` for open payments and challenges (the only funds the contracts hold for users).
- Resolver bonds held by `IfsoOutcomeResolver` (pull-paid).
- Creation fees passing through `FeeRouter` (never escrowed money).
- Claim-link secrets (in the URL fragment; whoever holds one can claim that payment).

## Actors
| Actor | What it can do |
|---|---|
| Sender | Creates payments; cancels a cancellable one or an unaccepted challenge; taps OK (releases to the recipient, except in two-party mode); moves its own refund addresses. |
| Recipient / acceptor | Claims a link payment; accepts a challenge; taps OK; declines (returns the money to the sender); moves its own refund address in a challenge. |
| Referee | Decides one APPROVE-referee payment: release to the recipient or return to the sender. Nothing else. |
| Anyone (keeper, stranger, either party) | Settles a decidable condition; refunds after expiry; relays signed claims, decisions and refund-address changes; proposes or disputes an outcome with a bond. |
| Owner multisig (2-of-3) | Fees for new payments (capped at 5 USDG each), pause of new entries, launch cap, the feed / price-id / resolver registry for new payments, resolver question creators and bond size, fee split recipients, a 48 h delayed panel change. No function reaches escrowed USDG (invariant R7). |
| Panel multisig | Decides disputed outcome questions inside its window; silence leads to VOID (escrows refund; each bond side gets half back, the other halves go to the FeeRouter), never to a forced result. |
| Resolver service | Registers questions (creator key) and proposes results from two or more independent sources. For a proposal by another address (review R3-H1): disputes it at once when two final sources agree on a different outcome; when its sources are pending, unavailable or conflicting it re-checks every tick and disputes only in a last-call slot (20 min before the 2 h window closes) if still unconfirmed, within a budget of `floor(float / bond) - 1` open last-call disputes (one bond always kept for a contradicted proposal), largest USDG amount first, and pages a human when over budget. Never finalizes a proposal it did not confirm. Trusted only as far as the bond and dispute window allow. |
| USDG issuer | Can freeze addresses, including the escrow contract. |
| Robinhood Chain sequencer | Orders transactions and may refuse to include some addresses. |
| Sybils / griefers | Many cheap accounts, spam proposals or disputes, front-running relayed transactions. |

## Risks and defences
| Risk | Defence | Residual risk |
|---|---|---|
| Claim link copied or front-run | The claim signature binds escrow id, recipient and condition hash under EIP-712 (chain id and contract in the domain); a copied transaction cannot change the recipient (`test_Link_FrontRunnerCannotRedirect`). The first valid claim binds the recipient. | Anyone who sees the link before the recipient can claim it (it works like cash). Short expiries, cancellable payments and private sending reduce this. |
| Link secret leaks from the page | The secret lives only after `#`; the page removes it from the address bar, loads no third-party scripts and uses a strict CSP. The server only sees the derived address. | Chat apps keep the message; malicious browser extensions. |
| Look-alike claim pages | Amount and condition are read from the chain; one canonical domain; a warning on the page. | Users on look-alike domains. |
| Stale or cherry-picked oracle round | AT_DEADLINE needs the last round at the deadline to be fresh (`maxStale`), else the first print inside `holdWindow`, else VOID. Round-id proofs stop a keeper from picking an older round, and a round after the deadline is not a proof of the deadline. | The feed's 0.5% deviation threshold: a price within about 0.5% of the level can resolve either way (disclosed). |
| Brief price spike | AT_DEADLINE is the default; TOUCH is opt-in and labelled "any feed update"; Pyth confidence must be within 2%; only registry feeds are allowed. | TOUCH can trigger on a short move (disclosed). |
| Fake Stock Token or feed | Feeds and price ids are allow-listed by the owner multisig; the feed-to-token pairing comes from the registry, never from the creator (`test_Validate_RegistryPairingAndMultiplier`). | A compromised multisig could list a bad feed for new payments only. |
| Stock split applied twice | The contract never multiplies; a changed or scheduled multiplier gives VOID or a create-time revert (`test_MultiplierChange_Voids`, `test_Validate_ScheduledSplitBeforeDeadlineRejected`). The multiplier that counts is the one **in force at the deciding price's time** (round `updatedAt`, Pyth `publishTime`), and it must be **provably** the creation snapshot (review R2-L1). ERC-8056 shows only the latest schedule, so: no schedule ever → the current value; latest schedule in force at the price → its new multiplier (and the token must report it); latest schedule still pending at settle → the current value; latest schedule that took effect **between the price and the settle** → VOID, because the value it replaced (the one in force at the price) is no longer visible, and two actions look exactly like one there. Unreadable fields VOID. A corporate action announced but not yet in force leaves a decided result standing (R1-L1), so the keeper settles before an announced `effectiveAt`. Tests: `test_R2_L1_*`, `testFuzz_R2_L1_TwoActions_DecidesOnlyOnTheSnapshotBasis`, Halmos `check_R2L1_TwoActionsDecideOnlyOnTheSnapshot` (any two actions, lazy or applied token), `test_R1_L1_*`, `testFork_MultiplierPairing`. | Conservative VOIDs around corporate actions: a decided result that is not settled before the next action takes effect VOIDs. Three or more actions where one lands after the price and a later one restores exactly the snapshot value, followed by a third still pending at settle, are not detectable from one schedule (SECURITY.md, accepted risks). |
| Wrong or colluding outcome result | Two or more agreeing sources before a proposal; anyone may propose or dispute with a bond; a separate panel multisig decides disputes; panel silence gives VOID; the evidence hash is on chain. | The panel is trusted on disputed questions. |
| Dispute griefing | A dispute costs a full bond (100 USDG default, 10 to 10,000); a losing disputer forfeits it (half to the winning proposer, half to the FeeRouter). Worst case is a delay of up to 72 h, then VOID. An OUTCOME escrow's expiry must be at least `earliestResolve + PROPOSAL_GRACE (2 days) + disputeWindow + panelWindow + 1 day`, read from the resolver at create time, so an honest proposal made up to 2 days late (sources publishing late, the service down for a day), disputed at the last second and answered by the panel at the very end of its window, still settles before expiry: the losing side cannot dispute once and wait for the escrow to expire into a VOID (review R1-M3 and R2-L2, `test_R1_M3_Outcome_DisputeRunsOutTheClock`, `test_R2_L2_LateProposal_DisputeStillRunsOutTheClock`). **Why a longer minimum and not a settle grace after expiry (R2-L2):** letting a FINAL question settle after expiry would race the refund that anyone may call after expiry, and making that refund wait on the question would block the one exit that must never be blocked. A longer create-time minimum changes nothing at settle or refund, adds no escrow bytes, and fails at create with a clear error. With the deployed windows (2 h, 72 h) the minimum is `earliestResolve + 6 days 2 hours`, inside the app's `earliestResolve + 7 days`. | A well-funded griefer can force VOIDs where the panel stays silent; panel response alerts mitigate it. A proposal made more than 2 days after `earliestResolve` (about 70 h with the app's 7-day expiry) and then disputed can still run past expiry into a VOID (SECURITY.md, accepted risks). The resolver service proposes at `earliestResolve`, alerts after 48 h without an agreed result, and is monitored. |
| Self-dispute (audit 2026-11-05 M-1) | Before the fix a party could propose and dispute its own proposal: whatever the panel said, it was credited both bonds (or got both back on panel silence), so it could send any OUTCOME question to the panel for free, lock the resolver service out of that question for up to 72 h, and on silence get a VOID (a free option for the losing side). **Fix: the economic split, not the address check.** A panel answer credits the winner its own bond plus `floor(bond / 2)` of the loser's; the loser's other `ceil(bond / 2)` is forfeited to the FeeRouter. Panel silence (`finalizeTimedOut`) credits each side only `floor(bond / 2)` and forfeits both other halves. So one owner holding the proposer AND the disputer address loses at least `bond / 2` when the panel answers (for, against or VOID) and a whole bond when it is silent. `dispute` also refuses `msg.sender == q.proposer` (`SelfDispute`), which only stops the one-address case; the split is what makes a second address pointless. Forfeits accrue in `forfeited` (no external call in `panelResolve` / `finalizeTimedOut`, so a USDG pause or freeze cannot block a question from reaching FINAL / VOID) and anyone forwards them with `forwardForfeits()`; the FeeRouter splits them 80/10/5/5 like any fee (80% to work, which funds the resolver's bond float). **Why silence forfeits both halves and not a refund:** nobody can tell who was right, and any rule that returns more than `bond * 3/4` to each side makes a self-dispute that nobody answers cheaper than `bond / 2`; returning whole bonds (the old rule) made it free. Both halves is the simple rule that also makes a dispute nobody answers cost the disputer as much as the proposer. **Honest resolver service, expected cost per dispute it is in:** disputes a contradicted proposal, panel answers: +`bond / 2`; its own proposal disputed by a griefer, panel answers: +`bond / 2` (the griefer loses a whole bond); a last-call dispute the panel rejects: -`bond` (unchanged); any of these with panel silence: -`bond / 2` (was 0). The worst case per open dispute is still one bond, so the existing `floor(float / bond) - 1` budget keeps the float solvent; silence is a panel failure that the studio controls and alerts on. PoC turned regression: `test/pocs/AuditM1SelfDispute.t.sol` (every branch, fuzzed bond); invariant OR5; Halmos `check_ResolverDisputeSplit`; FeeRouter suite drives a real resolver into the router. | A whale whose payment stake is far above `bond` can still self-dispute to delay a payment up to 72 h at a cost of `bond / 2`, and wins a VOID only if the panel stays silent (costing a whole bond). Panel liveness (alerts within the window) remains the defence; the owner can raise `bondAmount` (up to 10,000 USDG). |
| Wrong proposals by strangers | The resolver service fails closed without paying honest proposers out of its float (reviews R2-H1, R3-H1). A proposal its sources contradict (two final sources agreeing on another outcome) is disputed at once, using the last bond if needed. A proposal its sources cannot confirm yet (pending, unavailable, conflicting) is re-checked every tick and disputed only in the last-call slot (`RESOLVER_LAST_CALL_SECONDS`, default 20 min, under half the window) if still unconfirmed, while fewer than `RESOLVER_UNCONFIRMED_DISPUTE_BUDGET` (default `floor(float / bond) - 1`) last-call disputes are open and one bond stays in the float; questions with the most USDG in payments go first, the rest page a human (`resolver-dispute-budget`). A last-call dispute the panel rejects raises `resolver-last-call-lost`. Polymarket questions resolve no earlier than endDate + 24 h, after the expected UMA settlement, so honest proposals normally meet final sources. The service never finalizes a foreign proposal it did not confirm, checks foreign proposals first on every tick, and alerts on every foreign proposal and on any that reaches the end of its window unconfirmed (`app/test/reviewR3.resolver.anvil.test.ts`, property test `app/test/resolverPolicy.property.test.ts`). | Needs the service up, keyed and funded during the 2 h window (monitored; anyone else can still call `finalize` once the window closes). If sources stay pending to the window end (e.g. a disputed result upstream), the service disputes an honest proposal at last call and loses one bond (half to the proposer, half to the FeeRouter); the budget caps that loss and over budget a human must dispute within the window. |
| Sender cannot transact or receive (screened or frozen) | Refund is open to anyone after expiry; the caller picks the primary or alternate refund address per side; the sender can sign a refund-address change that anyone relays; bonds are pull-paid. | A USDG issuer freeze of the escrow contract itself stops every exit (disclosed). |
| One side's frozen address holds the other side's money (review R1-M4) | A VOIDed challenge pays each side on its own: each transfer is tried, and a side whose destination cannot receive is recorded as owed (`Voided` reports its destination as address 0) instead of reverting the whole refund. Anyone can later pay an owed side with `claimVoid(id, side, alt)`, only to that side's own preset destinations; the owed party may first point them elsewhere (`setRefundAddresses` for the sender, `setCounterRefundTo` for the acceptor, allowed only while that side is owed). A transfer that ran out of gas reverts the whole call, so a caller cannot starve a transfer (63/64 rule) to push a payable side into the owed state; the bound is `g/16` because USDG is a proxy and an out-of-gas in its inner frame hands back about 2/64 of the gas (R2-I1, `test_R2_I1_ProxyUsdg_StarvedRefundNeverMarksAPayableSideOwed`). Tests: `test_R1_M4_*`, invariants R4 and R6 with USDG freezes in the handler. | An owed side whose every destination stays frozen stays in the escrow until the issuer lifts the freeze or its owner redirects it (its own money). Off-chain, the keeper must call `claimVoid` for owed sides (app todo). |
| Relayed no-op signatures drain the relayer (review R1-M5, on-chain part) | A repeated OK by the same party and a refund-address change to the addresses already set revert with `NoChange`, so the relayer's simulation refuses them; a reverted call leaves the signer's nonce unchanged. Tests: `test_R1_M5_*`. | Rate limits per wallet and per /64 on the relaying routes are the app's part. |
| Keeper down | Every payment has an expiry (at most 400 days); refund is never paused and needs no special caller; expiry minimums leave room to settle (invariant R6, `testFuzz_RefundAlwaysWorksAfterExpiry`). | A met condition nobody settles before expiry goes back to the sender; the recipient's own page can settle it. |
| Challenge information edge | **PRICE AT_DEADLINE (review R1-M1): `acceptBy + maxStale < deadline`, checked in `validate`.** The deciding price is either the last round at or before the deadline that is at most `maxStale` old (so its `updatedAt >= deadline - maxStale > acceptBy`) or the first print after the deadline (`> deadline > acceptBy`). Either way it is written strictly after the last moment anyone can accept, including when the market is closed (a Friday close that is fresh enough to decide a Saturday deadline is, by the same rule, written after `acceptBy`). Chosen over a settle-time "round must be after acceptance" rule because it needs no change to `evaluate` (the keeper's shadow check calls it), adds nothing to the escrow's size, and fails at create time with a clear error instead of a surprise VOID. Cost: the accept window ends `maxStale` before the deadline, so the app picks a small `maxStale` for challenges. **PRICE TOUCH: two-sided is refused** (review R1-M2): TOUCH can only end TRUE or VOID, so the sender could never win, and an invitee could accept after a cross. OUTCOME: accept closes by `closeTime` (kickoff). Tests: `test_R1_M1_*`, `testFuzz_R1_M1_DecidingRoundIsAfterAcceptBy`, `test_R1_M2_*`, `test_TouchChallenge_RefusedAtCreation`, invariant `invariant_NoKnowableChallengeCreated`. | Insider information is not addressed. A price can be known off-chain seconds before its round is written, so an `acceptBy` right at `deadline - maxStale` gives the invitee a small edge the sender chose to allow. Polymarket markets that resolve before `closeTime` are an app-level question (R1-L3, app todo). |
| Honor-system abuse in challenges | Two-sided payments cannot use TIME or two-party APPROVE, and the referee cannot be a party. | Referee collusion (pick a referee both sides know). |
| Gasless create re-pointed | The EIP-3009 nonce commits to every create parameter; any change breaks the signature (`test_CreateWithAuthorization_TamperedParamsRevert`); accept nonces bind the acceptor and its refund address. | None known. |
| Replayed decisions or refund redirects | Per-signer nonces, deadlines, EIP-712 domain with chain id and contract. | None known. |
| Reentrancy, token quirks | `nonReentrant` on every state-changing user entry point; a single immutable token (USDG); checked-transfer helpers. A contract that reads `getEscrow` from inside the Pyth fee refund callback during `settle` sees the pre-settle record (read-only reentrancy; no state can change). | Integrators should not read escrow state from inside that callback. |
| Launch cap removed or lowered | The cap gates only new creates and accepts; exits never depend on it (`test_Cap_LoweredDoesNotBlockExits`). | The owner multisig can raise or remove the cap at once (see SECURITY.md, accepted risks). |
| Deploy mistakes | The deploy script reads no private key, refuses on every chain except a local anvil (31337) unless armed by env flag and a local file (review R1-I6), and asserts owners, fees, cap, feeds and panel after deploying; `PostDeployCheck` re-runs the assertions from the deployment file. On Robinhood Chain the assertions also require: launch cap on and at most 1,000 USDG; Pyth not wired (`pyth = 0`, immutable, so the unproven path cannot be switched on by an owner call, review R1-L2); owner and panel are official SafeProxy contracts (runtime codehash) on an official SafeL2 1.4.1 / 1.3.0 singleton, threshold >= 2, no module, no guard (review R1-L4, `test_R1_L4_*`, `testFork_R1_L4_SafeCheck`). | Values must still be reviewed before each real deploy. Turning Pyth on is a new evaluator and escrow deploy plus a review round. |
